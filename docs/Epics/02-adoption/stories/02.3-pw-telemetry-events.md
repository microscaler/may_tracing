# Story 02.3: pw_telemetry — business events attributed to the request

**Repo:** microscaler/PriceWhisperer (`microservices/pw_telemetry`)

## Description

`pw_telemetry::record` emits standalone events precisely because the thread-local span
was unsafe to touch (its module docs say so). With the coroutine context available, the
events become children of the request span — `operation`, `outcome`, `error_kind` and
`symbol` land inside the `http_request` trace instead of beside it — with no change to
the call sites in the 12 services.

## Functional Requirements

- [ ] `pw_telemetry` depends on `may_tracing` (workspace dependency in `microservices/Cargo.toml`)
- [ ] `emit_tracing`: each `tracing::<level>!(…)` becomes `may_tracing::<level>_in_current!(…)`
      with identical fields and message
- [ ] The `catch_unwind` around the emit stays (documented as belt-and-braces now)
- [ ] `init_worker` (Tokio workers/ingestors) untouched: on a Tokio thread `current()` is the
      thread slot, which nobody sets → root events, same as today
- [ ] Module docs rewritten: the "handlers run on separate coroutines so events are not
      nested" paragraph becomes "events are parented on the coroutine's span (may_tracing);
      inside a BRRTRouter handler that is the request span"

## Non-Functional Requirements

- [ ] No call-site changes in any service (`grep -rn "pw_telemetry::" microservices/trader` unchanged)
- [ ] The OpenSearch log fields (`operation`, `outcome`, `error_kind`, `symbol`, `duration_ms`, `detail`)
      unchanged — the Discover saved searches keep working

## Acceptance Criteria

1. Under `with_span(req, …)`, `pw_telemetry::info(BusinessEvent::new("x", Ok))` produces an
   event with parent `req` (recording layer, unit test in `pw_telemetry`)
2. Outside any context (a Tokio ingestor), the same call produces a parentless event
3. In OpenSearch, a `market_stream_open` event appears inside the `/market/stream` request
   trace
