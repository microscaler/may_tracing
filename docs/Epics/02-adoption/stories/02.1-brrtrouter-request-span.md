# Story 02.1: BRRTRouter — the request span is the coroutine context, never entered

**Repo:** microscaler/BRRTRouter

## Description

BRRTRouter is where the panic class is manufactured: `server/service.rs` creates
`http_request` and holds `span.enter()` for the whole request across the dispatch to the
handler coroutine, and `middleware/tracing.rs` enters two throwaway spans around events.
Replace the enter with the coroutine context, spawn handlers with the context, and record
the middleware's events on the request span. The OTEL export of `http_request` (start,
end, status, duration, stack_used_kb) is unchanged: `RequestLogger` already holds the
span handle and records fields on drop.

## Functional Requirements

- [ ] Inventory first: `grep -n "\.enter()\|\.entered()\|Span::current()\|in_scope(" src/`
      pasted into the story's Notes with a disposition per line (context / no-yield keep /
      remove)
- [ ] `server/service.rs`: `let _enter = span.enter();` → `let _ctx = may_tracing::set_current(span.clone());`
      (the guard lives as long as the old one did; nothing else in the function changes)
- [ ] Handler dispatch: wherever the handler coroutine is spawned (`dispatcher::core`, the
      `#[handler]`-generated glue, or `service.rs`), use `may_tracing::spawn_with(builder, request_span, f)`
      so the handler's `current()` is the request span from its first instruction
- [ ] `middleware/tracing.rs`: `before` → `may_tracing::info_in_current!(method = ?req.method, path = %req.path, handler = %req.handler_name, "Request started")`;
      `after` → `may_tracing::info_in_current!(status = res.status, latency_ms = …, "Request completed")`;
      the `http_request`/`http_response` throwaway spans are deleted
- [ ] `security/jwks_bearer` (2 spans) and `security/shadow.rs` (1 span): confirmed
      yield-free → keep `enter()` with `// no-yield: <why>`; or convert to
      `child_span!` + no enter — choose per site, record in Notes
- [ ] `may_tracing = { git = …, tag = "v0.1.0" }` in `Cargo.toml`
- [ ] The request logger's `span` field and its `record(...)` calls untouched

## Non-Functional Requirements

- [ ] No behavioural change to responses, status codes, logging fields, or the
      `RequestLogger` output (compare a log line before/after in the Notes)
- [ ] No new allocation per request beyond one `Span::clone`
- [ ] The e2e suite BRRTRouter ships (`tests/`) green; the PriceWhisperer `spec-conformance`
      Tilt resource green after deploy

## Acceptance Criteria

1. `grep -c "\.enter()\|\.entered()" src/server src/middleware src/dispatcher` is 0
2. Inside any handler, `may_tracing::current()` is the `http_request` span (a test handler
   in BRRTRouter's own test suite asserts `!current().is_none()` and the name)
3. A `lifeguard`-style child span created in a handler (test: `child_span!`) has the
   request span as parent in a recording layer
4. The trace view in OpenSearch shows `http_request` with the middleware's two events
   *inside* it instead of two sibling one-event spans
5. The PriceWhisperer 200 × 40 load run: 0 tick failures, 0 market restarts (with 02.2
   this is the epic's acceptance; here it is the smoke)
