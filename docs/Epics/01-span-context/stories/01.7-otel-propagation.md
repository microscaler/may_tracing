# Story 01.7: OTEL propagation helpers (`otel` feature)

## Description

Distributed tracing needs two conversions at process boundaries: the current span → a
W3C `traceparent` header on an outbound call, and an inbound `traceparent` → a span whose
parent is the remote context. `tracing-opentelemetry` does both via
`Span::current().context()` and `span.set_parent(cx)` — which read the thread-local. This
story provides the same two operations against the coroutine context, behind the `otel`
feature, so a BRRTRouter handler calling another service (or the BFF calling a service)
keeps one trace across the hop without touching the thread stack.

## Functional Requirements

- [ ] Feature `otel` enabling `tracing-opentelemetry` and `opentelemetry` (versions
      matching what BRRTRouter pins — check before adding)
- [ ] `pub fn traceparent_of_current() -> Option<String>`: `current().context()` via
      `OpenTelemetrySpanExt`, then `TraceContextPropagator` into a `HashMap` carrier; `None`
      when the current span is none or has no OTEL context
- [ ] `pub fn inject_current(headers: &mut impl Injector)`: the general carrier form
      (`traceparent` + `tracestate`), for callers with a header map
- [ ] `pub fn span_with_remote_parent(name: &'static str, carrier: &impl Extractor) -> Span`:
      `TraceContextPropagator::extract` → `span!(parent: None, INFO, name)` +
      `set_parent(cx)`; a root span with the remote link when the carrier has one, a plain
      root span otherwise
- [ ] `pub fn span_with_remote_parent_str(name, traceparent: &str, tracestate: Option<&str>) -> Span`
      for callers holding strings
- [ ] Rustdoc examples for both directions; a note that the *propagator* is the global one
      (`opentelemetry::global::get_text_map_propagator`) so a consumer's choice of
      propagator is honoured

## Non-Functional Requirements

- [ ] No feature ⇒ none of these symbols exist and no OTEL crate is compiled
- [ ] No thread-local read anywhere in the module (grep `Span::current` → zero hits)
- [ ] Works without an OTEL layer installed: `traceparent_of_current()` is `None`,
      `span_with_remote_parent` still returns a usable span

## Acceptance Criteria

1. With a `tracing_opentelemetry::layer()` on a registry and a `with_span(a, …)` scope,
   `traceparent_of_current()` is `Some("00-<trace id of a>-<span id of a>-01")`
2. `span_with_remote_parent("in", &carrier)` under that layer yields a span whose OTEL
   `SpanContext.trace_id` equals the carrier's
3. Without the layer, (1) is `None` and (2) returns a span that records normally
4. Round trip: inject from one "process" (a coroutine), extract in another, both spans
   share a trace id in the exported batch (in-memory exporter)

## Definition of Done

- [ ] Tests green with `--features otel`; the no-feature build unaffected
- [ ] CI matrix includes `--all-features` (already, from 01.1)
- [ ] Commit message: `feat(otel): traceparent in/out against the coroutine context (Epic 01.7)`

## Tests

```rust
// tests/otel.rs  (cfg(feature = "otel"))
#[test]
fn round_trip_shares_trace_id() {
    let exporter = opentelemetry_sdk::testing::trace::InMemorySpanExporter::default();
    let provider = /* SdkTracerProvider with the exporter, simple processor */;
    let layer = tracing_opentelemetry::layer().with_tracer(provider.tracer("t"));
    let _s = tracing::subscriber::set_default(tracing_subscriber::registry().with(layer));
    let mut carrier = std::collections::HashMap::new();
    may_tracing::with_span(tracing::info_span!("client"), || may_tracing::inject_current(&mut carrier));
    let server = may_tracing::span_with_remote_parent("server", &carrier);
    drop(server);
    provider.force_flush();
    let spans = exporter.get_finished_spans().unwrap();
    assert_eq!(spans.len(), 2);
    assert_eq!(spans[0].span_context.trace_id(), spans[1].span_context.trace_id());
}
```
